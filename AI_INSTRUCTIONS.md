# Project Context: Smart Greenhouse Automation with MicroSD (Phase 1)

This document serves as the baseline instructions and context for any AI Agent or future programming session. The AI must strictly follow the hardware architecture and software structure described below in any code proposal or modification.

## 1. Architecture and Main Constraints
- **Microcontroller:** ESP32-C3 Super Mini (RISC-V architecture).
- **Development environment:** VS Code with the PlatformIO extension (Arduino framework).
- **Code storage:** GitHub Repository.
- **Operating mode:** Fully OFFLINE. The board generates its own local Wi-Fi (Access Point) and hosts a local web page at `192.168.4.1` for monitoring from a phone.
- **Data logging:** Periodically saves data from all sensors and the total pumped volume to the `/date_solar.csv` file on the MicroSD card (FAT32 formatted).
- **Automation logic:** State machine for sequential irrigation based on water volume (flow meters), triggered at a fixed time from the RTC.

## 2. Hardware Configuration & Pin Mapping (`include/config_hardware.h`)
All physical pins are mapped through constants and MUST be referenced in code by the variable names below:

- `PIN_SDA` (GPIO 7) & `PIN_SCL` (GPIO 6) -> I2C communication for the DS3231 RTC clock. GPIO 0/1 avoided — the ESP32-C3's hardware I2C peripheral does not work correctly on those pins on this board.
- `PIN_SD_MISO` (GPIO 2), `PIN_SD_MOSI` (GPIO 3), `PIN_SD_SCK` (GPIO 4), `PIN_SD_CS` (GPIO 10) -> Dedicated SPI bus for the MicroSD card module. GPIO 2 is a strapping pin (HIGH = normal boot) — has a physical 10kΩ pull-up resistor to 3.3V on the MISO line.
- `PIN_PUMP` (GPIO 5) -> Relay 1 (220V AC water pump).
- `PIN_VALVE_Z1` (GPIO 8) -> Relay 2 (Zone 1 solenoid valve - 12V DC).
- `PIN_VALVE_Z2` (GPIO 9) -> Relay 3 (Zone 2 solenoid valve - 12V DC).
- `PIN_TEMP_SENSORS` (GPIO 0) -> One-Wire bus for two waterproof DS18B20 sensors (Soil and Water, distinguished by ROM address). Requires a 4.7kΩ pull-up resistor to 3.3V. The address-to-role mapping is user-editable from `/config` (see Section 3), not hardcoded — replacing a sensor just needs re-mapping, not a reflash.
- `PIN_DHT22` (GPIO 1) -> Digital sensor for air climate (Temperature + air humidity). Requires a physical 10kΩ pull-up resistor to 3.3V on the DATA line.
- **GPIO1 history:** on a since-replaced ESP32-C3 chip, GPIO1 was conclusively dead (failed OneWire, DHT22, and SPI chip-select). That was isolated to that specific chip's silicon — the replacement chip's GPIO1 works normally, confirmed by real DHT22 readings. See the "GPIO1 HISTORY" comment in `config_hardware.h` for the full story if similar symptoms ever reappear.
- `PIN_FLOW_Z1` (GPIO 20) -> Zone 1 flow meter (YF-S201). Uses a hardware interrupt (`RISING`). The sensor is powered at 5V, and the output signal is 5V — a physical voltage divider on the signal line (R1=10kΩ, R2=20kΩ to GND) brings the signal down to 3.33V before the GPIO.
- `PIN_FLOW_Z2` (GPIO 21) -> Zone 2 flow meter (YF-S201). Uses a hardware interrupt (`RISING`). Same voltage divider as Zone 1.
- **BMP180 barometer** (pressure + altitude) -> Shares the `PIN_SDA`/`PIN_SCL` I2C bus with the DS3231 RTC. Fixed I2C address `0x77`, no conflict with the RTC's `0x68`. No dedicated pin needed — just VCC/GND/SDA/SCL wired in parallel with the RTC.

**Relay logic:** The relay modules used are active `LOW` (`0V` = On, `3.3V/5V` = Off). The code uses the constants `RELAY_ON` and `RELAY_OFF`. Physically: the VCC↔JD-VCC jumper is removed — JD-VCC is powered at 5V (relay coils) and VCC at 3.3V (logic/optocouplers). Each IN line (GPIO 5, 8, 9) has a 1kΩ series resistor to the ESP32-C3 pin.

## 3. System Parameters & Settings
- `include/config_system.h` (compile-time):
  - `WIFI_SSID` = "greenhouse", `WIFI_PASSWORD` = "!Green2024"
  - `WIFI_STA_SSID`/`WIFI_STA_PASSWORD`/`WIFI_STA_TIMEOUT_MS` -> optional home-network fallback
  - `DEFAULT_START_HOUR_Z1`, `DEFAULT_START_MINUTE_Z1`, `DEFAULT_START_HOUR_Z2`, `DEFAULT_START_MINUTE_Z2`, `DEFAULT_ZONE1_ENABLED`, `DEFAULT_ZONE2_ENABLED`, `DEFAULT_TARGET_VOLUME_Z1`, `DEFAULT_TARGET_VOLUME_Z2`, `DEFAULT_PULSES_PER_LITER`, `DEFAULT_SEA_LEVEL_PRESSURE_PA`, `DEFAULT_ADDR_SOIL`, `DEFAULT_ADDR_WATER` -> first-boot defaults only (see below). Z2's default start time is 30 minutes after Z1's specifically so a fresh board doesn't default both zones to the exact same minute (see the State Machine section for why that matters). Both zones default enabled.
- `include/app_settings.h` / `src/app_settings.cpp` (runtime, editable from `/config`):
  - `startHourZ1`/`startMinuteZ1`, `startHourZ2`/`startMinuteZ2` -> Each zone's own independent daily trigger time — not a single shared schedule. See the State Machine section for how the scheduler and manual triggers interact.
  - `enabledZ1`, `enabledZ2` -> Per-zone on/off switch, independent of the schedule/volume settings. When `false`, that zone runs neither on its own schedule nor via its manual `/water-zone1`/`/water-zone2` button — enforced in two places for defense-in-depth: the `irrigationLoop()` `STOPPED`-case schedule check skips a disabled zone's time match entirely (so a disabled zone doesn't even attempt-and-refuse every loop tick, which would otherwise starve its 60s dedupe window from ever resetting), and `startZone1()`/`startZone2()` themselves also refuse if their zone is disabled (covers the manual web-button path). If a zone is disabled while it's actively running, `handleConfigPost()` calls `stopAll()` immediately rather than letting the in-progress cycle finish. The other zone, and Stop Now, are unaffected. Saved settings, calibration, and last-watered history for a disabled zone are untouched — re-enabling needs no reconfiguration. Toggled via a checkbox per zone on `/config`'s "Irrigation Settings" card.
  - `targetVolumeZ1`, `targetVolumeZ2` -> Water volume in liters allocated to each zone.
  - `maxZoneMinutes` -> Safety cutoff (shared by both zones): `irrigationLoop()` force-stops a zone (via `stopAll()`) if it runs this long without reaching its target volume — protects against a stuck valve or a flow meter that stopped reporting pulses, which would otherwise leave the pump/valve energized indefinitely. Sets `irrigationFault`/`irrigationFaultMsg` (see `globals.h`) so the cause is visible on the dashboard until the next cycle starts.
  - `pulsesPerLiter` -> YF-S201 flow meter calibration factor (shared by both zones); `irrigation.cpp`, `sensors.cpp`, `sd_logger.cpp`, and `web_server.cpp` all read this instead of a fixed constant.
  - `seaLevelPressurePa` -> Local sea-level reference pressure (Pa) used by `bmp.readAltitude()` for accurate altitude; edited in hPa on the web UI and converted on save.
  - `addrSoil`, `addrWater` -> 16-char hex DS18B20 ROM addresses currently mapped to each role, or `""` if a role is unassigned. Saved via the dedicated `saveSensorMapping()` function (not the general `saveAppSettings()`) from the "DS18B20 Sensor Mapping" card on `/config`, which lists every sensor actually detected on the bus (`getDS18B20Count()`/`getDS18B20AddressAt()` in `sensors.h`) so a replaced sensor can be re-mapped without a reflash. Picking "Unassigned" for a currently-mapped sensor correctly clears that role (fixed bug: the save handler used to only ever *set* `addrSoil`/`addrWater` when a dropdown said soil/water, never *clear* them when a previously-mapped sensor was explicitly set back to "Unassigned"). `sensors.cpp`'s `applySensorMapping()` converts these hex strings into the `DeviceAddress` byte arrays the DallasTemperature library needs — and must be called again after any mapping change to take effect immediately (not just at boot) — zeroing the cached address when the string is empty (a real DS18B20 ROM can never be all-zero) rather than leaving a stale address in place, which was a second bug: unassigning used to have no runtime effect because the cached lookup address was never actually cleared.
  - `lastWateredZ1`/`lastVolumeZ1`, `lastWateredZ2`/`lastVolumeZ2` -> Each zone's own most recently *completed* run, tracked independently since zones no longer complete as one combined cycle. Not user-edited — written by `irrigation.cpp` via `saveLastWateredZ1()`/`saveLastWateredZ2()` when that zone finishes, shown on the dashboard's Water Volumes card as two separate lines. `"Never"` / `0` until that zone's first-ever completion.
  - Persisted to flash via `Preferences` (NVS, namespace `"ghouse"`). `loadAppSettings()` is called once in `setup()`; `saveAppSettings()` is called by the `/config` POST handler whenever the user submits new values. Consuming modules read these globals directly instead of `config_system.h` macros.

## 3b. Device Registry (`include/device_registry.h` / `src/device_registry.cpp`)
Tracks every MAC address that has ever connected to the Access Point, persisted in flash (NVS, namespace `"devices"`). `refreshConnectedDevices()` pulls the live station list via `esp_wifi_ap_get_sta_list()` and merges newly-seen MACs into the persisted list. Each known device can have a user-assigned `name` and `type` (stored per-MAC as `n_<MAC>`/`t_<MAC>` keys), edited from the `/connections` page — each device gets its own `<form>` with a hidden `mac` field plus `name`/`type` fields, using a `formaction` override on the second submit button so one form can post to either `/connections` (save) or `/connections/forget` (remove via `forgetDevice()`, which also clears its NVS keys) without nesting `<form>` tags. Note: forgetting a still-connected device just gets it re-added on the next `refreshConnectedDevices()` call — this is meant for devices that no longer connect, not for kicking one off the network (there's no access-control mechanism here, only the AP password governs who can join).

## 5. State Machine Logic
The system moves through three states (`enum WateringState`), one shared state machine covering both zones since they share a single pump:
1. `STOPPED`: Checks each zone's own schedule (`startHourZ1`/`startMinuteZ1` and `startHourZ2`/`startMinuteZ2`), gated on that zone's `enabledZ1`/`enabledZ2` flag, independently, plus watches for a manual `/water-zone1` or `/water-zone2` request (also gated on the same flag, inside `startZone1()`/`startZone2()`). **The two zones are not a combined cycle** — each is scheduled, started, and completed on its own; there is no automatic chaining from Zone 1 into Zone 2 the way earlier versions of this project worked.
2. `WATERING_ZONE_1`: Opens valve 1 (valve 2 forced off) and starts the pump. Counts pulses from flow meter 1 until Zone 1's own target volume is reached, then saves an SD report (`saveSDReport(volZ1, 0)` — Zone 2's column is `0` since it didn't run this session), records `saveLastWateredZ1()`, and returns to `STOPPED`.
3. `WATERING_ZONE_2`: Opens valve 2 (valve 1 forced off), pump on. Counts pulses from flow meter 2 until Zone 2's own target volume is reached, then `saveSDReport(0, volZ2)`, `saveLastWateredZ2()`, and returns to `STOPPED`.

**Mutual exclusion:** `startZone1()`/`startZone2()` both refuse (log and no-op, return `false`) if `currentState != STOPPED` — since one shared pump feeds both valves, they can never run concurrently. If one zone's scheduled minute arrives while the other zone is still running, that trigger is simply skipped for the day (not queued) — each zone has its own 60-second dedupe window (`lastStartAttemptZ1`/`lastStartAttemptZ2`) so a missed exact-minute match doesn't retry every loop tick. If both zones' schedules land on the exact same `STOPPED` tick, `irrigationLoop()`'s `switch` checks Zone 1 first, so Zone 1 wins that day — this is why the default Z2 start time is offset 30 minutes from Z1's (see `config_system.h`), to avoid that degenerate case out of the box. Manual triggers follow the same rule: `/water-zone2` while Zone 1 is running just logs "ignored" and does nothing.

**Safety timeout:** each of the two watering states also checks elapsed time against `maxZoneMinutes`. If a zone runs that long without reaching its target volume — e.g. a stuck valve or a flow meter that stopped reporting pulses — `irrigationLoop()` force-stops via `stopAll()` and sets `irrigationFault`/`irrigationFaultMsg`, shown as a red banner on the dashboard until the next cycle starts (manual or scheduled) clears it. Without this, a broken flow meter would leave the pump/valve energized indefinitely.

**Manual override:** the dashboard's "Manual Control" card exposes `/water-zone1` and `/water-zone2` (each starts only that zone; hidden — replaced by a "cycle already running" hint — whenever `currentState != STOPPED`) and `/stop` (calls `stopAll()` unconditionally, safe to call anytime) — all POST-only with a JS confirm dialog.

## 6. Future Development — Not Yet Implemented (parts not yet purchased)

**Soil moisture sensor (high value — closes the loop on irrigation).** Right now irrigation triggers purely on a fixed time + a target volume from the flow meters — it has no idea whether the soil actually needs water (soil *temperature* is measured via DS18B20, but not moisture). Adding this sensor is the single change most aligned with the project's actual "smart automation" goal, since it would let watering respond to real soil conditions instead of a blind schedule.

- **Hardware constraint:** the ESP32-C3 only has 5 ADC-capable pins (GPIO0–4, ADC1 only — no usable ADC2), and all 5 are already committed (GPIO0=DS18B20, GPIO1=DHT22, GPIO2/3/4=SD SPI). A standard analog capacitive soil moisture sensor cannot be wired directly without giving up one of those.
- **Chosen approach (parts confirmed available from Romanian retailers, not yet bought):**
  - [DFRobot Gravity Capacitive Soil Moisture Sensor, IP65 waterproof](https://magazin-roboti.ro/gravity-senzor-capacitiv-de-umiditate-a-solului-impermeabil-ip65-arduino-esp32-rpi/) — corrosion-resistant, suitable for permanent soil burial.
  - [ADS1115 16-bit I2C ADC module](https://sigmanortec.ro/en/modul-convertor-analogic-la-digital-adc-ads1115-16-biti) (also at [optimusdigital.ro](https://www.optimusdigital.ro/en/analog-to-digital-converters-adcs/1696-ads1115-cjmcu-digital-analogic-converter-module-adc.html), [ardushop.ro](https://ardushop.ro/en/modules/22-16-bit-adc-4-channel-module-ads1115-6427854011626.html)) — converts the sensor's analog output to I2C, joining the existing shared bus (GPIO6/7, alongside the RTC at 0x68 and BMP180 at 0x77) instead of needing an ADC pin. Address is jumper-selectable (0x48–0x4B), no conflict with existing devices.
  - Alternative (not sourced domestically): [Adafruit STEMMA Soil Sensor](https://botland.store/humidity-sensors/14431-stemma-soil-moisture-sensor-adafuit-4026-5904422307301.html) via Botland (Poland, EU-to-EU shipping) — natively I2C, simpler wiring, no ADS1115 needed.
  - Once acquired: add to `sensors.cpp` following the BMP180 pattern (shares the I2C bus, own status string, own globals), surface on the dashboard/Connections page, log to SD — and, unlike the other sensors, actually use the reading to gate `irrigationLoop()`'s watering decision in `irrigation.cpp`, not just display it.

**AT24C256 I2C EEPROM — low priority, likely unnecessary.** Considered as extra persistent storage, but `Preferences`/NVS already handles all current settings/calibration/mapping data and the SD card already handles bulk logging — an external EEPROM would mostly duplicate existing capability. Its only edge over NVS is higher write endurance (~1M cycles vs. flash's ~100K), which doesn't matter at the current write frequency (manual `/config` edits only). Note: **an EEPROM may already be physically present and unused** — the I2C scan found a device at address `0x50`, almost certainly the onboard AT24C32 EEPROM common on ZS-042-style DS3231 RTC breakout boards. Check that before buying a new AT24C256 if a use case ever justifies one.
